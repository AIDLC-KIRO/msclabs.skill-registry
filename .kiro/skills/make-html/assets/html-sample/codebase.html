System Overview & Architectureภาพรวมระบบและสถาปัตยกรรม

The system is a multi-service monolith: three Node processes deploy from a single repository and share one PostgreSQL database. Communication follows a hub-and-spoke pattern where the Event Bridge is the central broker between the external OPD Queue system and internal consumers — the REST API service and the browser clients. Reads are served from process memory instead of the database, and all external data arrives from TrakCare on a fixed schedule.ระบบมีลักษณะเป็นโมโนลิธแบบหลายเซอร์วิส คือมี 3 โปรเซส Node ที่ deploy จาก repository เดียวและใช้ฐานข้อมูล PostgreSQL ร่วมกัน การสื่อสารใช้รูปแบบ hub-and-spoke โดย Event Bridge เป็นตัวกลางระหว่างระบบคิว OPD ภายนอกกับผู้ใช้ข้อมูลภายใน ทั้งเซอร์วิส REST API และเบราว์เซอร์ของผู้ใช้ การอ่านข้อมูลดึงจากหน่วยความจำของโปรเซสแทนการคิวรีฐานข้อมูลทุกครั้ง และข้อมูลจากภายนอกทั้งหมดถูกดึงมาจาก TrakCare ตามตารางเวลาที่กำหนดไว้

Key Architectural Decisionsการตัดสินใจเชิงสถาปัตยกรรมที่สำคัญ

In-memory caching

Appointments, care providers and room details are loaded from PostgreSQL into Node process memory and served straight from RAM, keeping dashboard reads at sub-millisecond latency and cutting database load.ข้อมูลนัดหมาย แพทย์ผู้ให้บริการ และรายละเอียดห้องตรวจ ถูกโหลดจาก PostgreSQL เข้าหน่วยความจำของโปรเซส Node แล้วตอบกลับจาก RAM โดยตรง ทำให้การอ่านข้อมูลบนแดชบอร์ดเร็วในระดับต่ำกว่าหนึ่งมิลลิวินาที และลดภาระของฐานข้อมูล

Event-driven updates

Socket.IO pushes real-time notifications to every connected browser whenever a room assignment or patient status changes, so the dashboard reflects clinic floor activity without waiting for the next poll.Socket.IO ส่งการแจ้งเตือนแบบเรียลไทม์ไปยังทุกเบราว์เซอร์ที่เชื่อมต่ออยู่ทุกครั้งที่มีการเปลี่ยนห้องตรวจหรือเปลี่ยนสถานะผู้ป่วย ทำให้แดชบอร์ดสะท้อนสถานการณ์หน้างานได้ทันทีโดยไม่ต้องรอรอบ polling ถัดไป

Temp table staging

Data pulled from TrakCare is written to temporary tables first, then compared with the main tables using SQL EXCEPT so that only genuinely new or changed rows are promoted — this is also how change events are detected.ข้อมูลที่ดึงจาก TrakCare จะถูกเขียนลงตารางชั่วคราวก่อน แล้วเปรียบเทียบกับตารางหลักด้วยคำสั่ง SQL EXCEPT เพื่อคัดเฉพาะแถวที่เพิ่มใหม่หรือเปลี่ยนแปลงจริงขึ้นไปใช้งาน ซึ่งเป็นกลไกตรวจจับเหตุการณ์การเปลี่ยนแปลงด้วย

Scheduled sync with a clinic-hours window

A dedicated scheduler service runs cron jobs against TrakCare: master data at 00:01, doctor schedules at 07:30, 11:30 and 16:30, and appointments every 60 seconds but only between 06:00 and 22:00 to match clinic operating hours.เซอร์วิสตัวจัดตารางเวลาแยกออกมาทำงาน cron เรียกข้อมูลจาก TrakCare คือข้อมูลหลักเวลา 00:01 ตารางแพทย์เวลา 07:30, 11:30 และ 16:30 และข้อมูลนัดหมายทุก 60 วินาที แต่ทำงานเฉพาะช่วง 06:00 ถึง 22:00 เพื่อให้ตรงกับเวลาทำการของคลินิก

3-Tier Architecture Viewมุมมองสถาปัตยกรรม 3 ชั้น (3-Tier)

Mapped onto a classic 3-tier model, the presentation tier is the React 16 SPA, the data tier is a single PostgreSQL database, and the middle tier is Express plus Socket.IO. That middle tier is not a clean business-logic layer: each file under server/modules holds its own route handlers, SQL strings, TrakCare calls and cache variable at once.เมื่อเทียบกับแบบจำลอง 3 ชั้นทั่วไป ชั้นนำเสนอคือเว็บแอป React 16 ชั้นข้อมูลคือฐานข้อมูล PostgreSQL เพียงชุดเดียว และชั้นกลางคือ Express ร่วมกับ Socket.IO แต่ชั้นกลางนี้ไม่ใช่ชั้นตรรกะทางธุรกิจที่แยกออกมาชัดเจน เพราะแต่ละไฟล์ใน server/modules มีทั้งตัวจัดการ route คำสั่ง SQL การเรียก TrakCare และตัวแปรแคชอยู่รวมกัน

Architecture by Database Server Instanceสถาปัตยกรรมแยกตาม Database Server Instance

The whole system runs on two hosts inside the internal-subnet internal network: an application server carrying all three PM2 services plus the React build, and a single PostgreSQL 14.2 instance holding every table. Production traffic reaches the services through a reverse proxy on app-host.CUSTOMER_DOMAIN using HTTPS on 8000 and WSS on 8443.ระบบทั้งหมดทำงานบนเครื่องสองเครื่องภายในเครือข่าย internal-subnet คือเครื่องแอปพลิเคชันที่รันเซอร์วิส PM2 ทั้งสามตัวพร้อมไฟล์ build ของ React และเครื่องฐานข้อมูล PostgreSQL 14.2 เพียงชุดเดียวที่เก็บทุกตาราง การใช้งานจริงเข้าถึงเซอร์วิสผ่าน reverse proxy ที่ app-host.CUSTOMER_DOMAIN โดยใช้ HTTPS พอร์ต 8000 และ WSS พอร์ต 8443

Single points of failure on both tiers: one PostgreSQL instance serves all 13 tables with no documented replica or failover, and the Event Bridge and Scheduler each run as a single fork-mode process, so a crash stops real-time updates or TrakCare sync entirely. PM2 cluster mode also gives each app-service worker its own in-memory cache, which can leave workers disagreeing. See the modernization findings.มีจุดล้มเหลวเดียวทั้งสองชั้น ฐานข้อมูล PostgreSQL ชุดเดียวรองรับทั้ง 13 ตารางโดยไม่มีเอกสารระบุ replica หรือระบบสำรอง ส่วน Event Bridge และ Scheduler ทำงานแบบ fork โปรเซสเดียว หากล่มจะทำให้การอัปเดตเรียลไทม์หรือการซิงก์ TrakCare หยุดทั้งหมด นอกจากนี้โหมด cluster ของ PM2 ยังทำให้ worker ของ app-service แต่ละตัวมีแคชในหน่วยความจำของตัวเอง ซึ่งอาจทำให้ข้อมูลระหว่าง worker ไม่ตรงกัน ดูรายละเอียดที่ ผลการประเมินความพร้อมสู่ความทันสมัย

Patterns & Anti-Patternsรูปแบบและ Anti-Patterns

Design Patternsรูปแบบการออกแบบ

In-memory cache

Every module in server/modules keeps a module-level variable holding its latest query result, and API endpoints answer from that variable. Reads land at roughly 0 ms; the trade-off is data up to 60 seconds stale.ทุกโมดูลใน server/modules เก็บตัวแปรระดับโมดูลที่บรรจุผลคิวรีล่าสุด และ API endpoint ตอบจากตัวแปรนั้น การอ่านจึงเร็วในระดับใกล้ 0 มิลลิวินาที แลกกับข้อมูลที่อาจเก่าได้ถึง 60 วินาที

Event-driven pub/sub via Socket.IO

The Event Bridge acts as message broker: external systems POST events, it writes to the database and emits, then the App Service and every browser subscribe and refresh. Six named events carry all real-time traffic.Event Bridge ทำหน้าที่เป็นตัวกลางรับส่งข้อความ ระบบภายนอกส่ง POST เข้ามา ตัวมันเขียนลงฐานข้อมูลแล้ว emit ต่อ จากนั้น App Service และทุกเบราว์เซอร์ที่ subscribe จะรีเฟรชข้อมูล เหตุการณ์ทั้งหมด 6 ชื่อรองรับการสื่อสารเรียลไทม์ทั้งระบบ

Temp table staging

TrakCare data lands in a temp table, is compared to the main table with SQL EXCEPT across all 23 fields, then new rows are inserted and changed rows updated one by one. A change flag tells downstream consumers to refresh.ข้อมูลจาก TrakCare ลงตารางชั่วคราวก่อน แล้วเทียบกับตารางหลักด้วย SQL EXCEPT ครบทั้ง 23 ฟิลด์ จากนั้นเพิ่มแถวใหม่และอัปเดตแถวที่เปลี่ยนแปลงทีละรายการ พร้อมส่งค่าธงบอกให้ระบบปลายทางรีเฟรชข้อมูล

Implicit repository

Each module owns one domain entity and encapsulates its queries, cache and TrakCare calls. The shape is repository-like without the abstraction: pgpool.js is the only shared data-access seam, used by all 8 data modules.แต่ละโมดูลดูแลเอนทิตีโดเมนหนึ่งชนิด และห่อหุ้มคิวรี แคช และการเรียก TrakCare ของตัวเองไว้ รูปแบบจึงใกล้เคียง repository แต่ไม่มีชั้น abstraction จริง โดย pgpool.js เป็นจุดร่วมเดียวของการเข้าถึงข้อมูล ซึ่งโมดูลข้อมูลทั้ง 8 ตัวเรียกใช้

Anti-PatternsAnti-Patterns

God component

src/routes/index.js runs to over 300 lines and owns all application state, data fetching, WebSocket connections, alarm logic and routing. Adding an endpoint or an event means editing this one file.src/routes/index.js มีความยาวกว่า 300 บรรทัด และถือทั้งสถานะทั้งแอป การดึงข้อมูล การเชื่อมต่อ WebSocket ตรรกะการแจ้งเตือน และการจัดเส้นทาง การเพิ่ม endpoint หรือเหตุการณ์ใดก็ต้องแก้ไฟล์เดียวนี้

Module-level mutable state

let dataInMem = [] at module scope creates hidden coupling: request handlers and background cron tasks mutate the same reference, and under PM2 cluster mode each worker holds its own copy.การประกาศ let dataInMem = [] ที่ระดับโมดูลสร้างการพึ่งพาที่มองไม่เห็น เพราะตัวจัดการคำขอและงาน cron เบื้องหลังแก้ค่าอ้างอิงเดียวกัน และในโหมด cluster ของ PM2 worker แต่ละตัวยังถือสำเนาของตัวเองแยกกัน

Mixed concerns

server/modules/patientAppointment.js combines HTTP route handlers, business logic, embedded SQL and TrakCare integration in one file, so any change requires understanding all four and none can be tested in isolation.server/modules/patientAppointment.js รวมตัวจัดการ route ของ HTTP ตรรกะทางธุรกิจ คำสั่ง SQL ที่ฝังอยู่ และการเชื่อมต่อ TrakCare ไว้ในไฟล์เดียว การแก้ไขจึงต้องเข้าใจทั้งสี่เรื่อง และไม่สามารถทดสอบแยกส่วนได้

Dead code retention

server/modules.old/ holds 16 full copies of active modules, plus scattered .old files and 50+ lines of commented-out code, leaving no clear answer to which version is authoritative.โฟลเดอร์ server/modules.old/ เก็บสำเนาเต็มของโมดูลที่ใช้งานอยู่ถึง 16 ไฟล์ พร้อมไฟล์ .old ที่กระจายอยู่ทั่วโครงการ และโค้ดที่คอมเมนต์ทิ้งไว้กว่า 50 บรรทัด ทำให้ไม่ชัดเจนว่าเวอร์ชันใดคือของจริง

Polling and push redundancy

The frontend polls the API every 6 seconds and also listens for Socket.IO events, then compares results with JSON.stringify. The same data is fetched twice and diffed expensively.ฝั่งหน้าเว็บทำ polling เรียก API ทุก 6 วินาที และยังฟังเหตุการณ์จาก Socket.IO ควบคู่กันไป แล้วเทียบผลด้วย JSON.stringify ทำให้ดึงข้อมูลชุดเดียวกันซ้ำสองทางและเปรียบเทียบด้วยวิธีที่สิ้นเปลือง

Security Analysisการวิเคราะห์ความปลอดภัย

Overall security risk is rated High. The application does apply Helmet, rate limiting, an API key, IP filtering and parameterized SQL, but two configuration choices undo much of that: TLS certificate validation is switched off in the Event Bridge process, and CORS is open to any origin. Authentication is fully delegated to TrakCare, so the app itself holds no user roles.ความเสี่ยงด้านความปลอดภัยโดยรวมอยู่ในระดับสูง ระบบมีการใช้ Helmet การจำกัดอัตราการเรียก API key การกรอง IP และคิวรี SQL แบบ parameterized อยู่แล้ว แต่การตั้งค่าสองจุดลดทอนมาตรการเหล่านั้นไปมาก คือการปิดการตรวจสอบใบรับรอง TLS ในโปรเซส Event Bridge และการเปิด CORS ให้ทุก origin นอกจากนี้การยืนยันตัวตนถูกส่งต่อไปยัง TrakCare ทั้งหมด ทำให้ตัวแอปไม่มีการกำหนดบทบาทผู้ใช้ของตัวเอง
